# وثيقة البنية المعمارية — تطبيق وِفرة

> مستقلة عن التصميم والمنطق والتقنيات. تشرح فقط كيف يُنظَّم الكود ولماذا.

---

## 1. الهدف من هذه البنية

الهدف الأساسي: **إمكانية تغيير أي تقنية لاحقًا (Hive، GetX، fl_chart) دون كسر باقي التطبيق**. يتحقق هذا عبر فصل واضح بين طبقة العرض وطبقة البيانات، بواسطة واجهات مجردة (Interfaces) — هذا هو تطبيق مبدأ **Dependency Inversion** (أحد مبادئ SOLID).

## 3. ملفات الثوابت — لماذا وكيف

بدل أن يُعرَّف اللون أو المقاس أو النص داخل كل شاشة على حدة (وهذا يعني تكرارًا وصعوبة تعديل لاحقًا)، كل شيء متكرر الاستخدام يُعرَّف **مرة واحدة فقط**:

### `app_colors.dart`
كل كود لوني من وثيقة التصميم (القسم 2) كـ `static const Color`، مع نسختين (Light/Dark) يختارهما `app_theme.dart` تلقائيًا حسب وضع الجهاز. مثال منطقي:
```
AppColors.primary
AppColors.secondary
AppColors.background
AppColors.danger
AppColors.dangerBg
```
أي شاشة تستدعي `AppColors.primary` — ممنوع كتابة كود hex مباشرة في أي ملف واجهة.

### `app_dimens.dart`
كل مقاس هندسي بمكان واحد، لضمان ألا يختار كل قسم مقاسات خاصة به:
```
AppDimens.cardRadius     // 16-20
AppDimens.paddingSm/Md/Lg
AppDimens.buttonHeight   // 48 كحد أدنى
AppDimens.iconSize
AppDimens.fontBody       // 16
AppDimens.fontHeading    // 20-22
```

### `app_strings.dart`
كل نص ثابت (عناوين الشاشات، تسميات الحقول، نصوص الأزرار، رسائل التحقق مثل "القيمة يجب أن تكون أكبر من صفر"، رسالة منع الحذف). فائدة إضافية: أي دعم لغوي مستقبلي يصبح تعديل ملف واحد فقط بدل البحث بكل الشاشات.

### `app_defaults.dart`
القيم الافتراضية عند أول تشغيل فقط (تُستخدم لتعبئة `settingsBox` أول مرة، ثم يعدّلها المستخدم من الإعدادات وتُحفَظ):
```
AppDefaults.tierLimitKwh   // 300
AppDefaults.tierPrice      // 600
AppDefaults.cycleMonths    // 2
AppDefaults.currencySymbol // "ل.س"
```

## 4. عزل الإعدادات

`modules/settings/` وحدة قائمة بذاتها بالكامل:
- `SettingsController` يحمل الحالة التفاعلية (وضع ليلي/نهاري، تعرفة الكهرباء، مدة الدورة).
- `ISettingsRepository` (واجهة) + `HiveSettingsRepository` (تنفيذ).
- يُسجَّل بـ `Get.put(permanent: true)` عند بدء التطبيق (وليس Lazy) لأنه مطلوب في كل الشاشات تقريبًا (الألوان الحية، رمز العملة)، بعكس باقي الـ Controllers التي تُحمَّل فقط عند فتح شاشتها.

## 5. حقن الاعتماديات (Dependency Injection)

### الفائدة هنا تحديدًا
1. الـ Controller لا يُنشئ الـ Repository بنفسه، بل يستلمه جاهزًا — يفصل "من يخزّن" عن "من يستخدم البيانات".
2. تبديل التقنية = تغيير نقطة تسجيل واحدة، بدون لمس أي Controller.
3. يسهّل الاختبار مستقبلًا عبر حقن نسخة وهمية (Mock) بدل الحقيقية.

### كيف يتحقق بـ GetX
كل Module له `Binding` خاص:
```dart
class CategoriesBinding extends Bindings {
  @override
  void dependencies() {
    Get.lazyPut<ICategoryRepository>(() => HiveCategoryRepository());
    Get.lazyPut<CategoriesController>(() => CategoriesController(Get.find()));
  }
}
```
الـ `CategoriesController` يستقبل `ICategoryRepository` في الـ constructor، ولا يعرف أنها Hive إطلاقًا. `Get.lazyPut` ينشئ الاعتماد فقط عند أول استخدام ويحذفه تلقائيًا عند إغلاق الشاشة (توفير موارد)، بعكس `Get.put(permanent:true)` المحجوزة للإعدادات فقط.

## 6. SOLID / DRY / أنماط التصميم — التطبيق العملي

| المبدأ/النمط | كيف يظهر هنا |
|---|---|
| Single Responsibility | كل Controller يدير شاشة واحدة، كل Repository يدير كيان بيانات واحد |
| Open/Closed | إضافة صنف/منتج جديد لا تتطلب تعديل كود موجود |
| Liskov Substitution | أي تنفيذ بديل لواجهة Repository قابل للاستبدال دون كسر الكود |
| Interface Segregation | كل Repository له واجهة صغيرة خاصة به، لا واجهة ضخمة موحّدة |
| Dependency Inversion | الـ Controllers تعتمد على الواجهات المجردة لا على Hive مباشرة |
| DRY | الثوابت والتحقق (Validators) والتنسيق (Formatter) بملف واحد يُستدعى من كل مكان |
| Repository Pattern | الفاصل الأساسي بين منطق العمل والتخزين |
| Singleton (عبر GetX) | `SettingsController` نسخة واحدة تعيش طوال عمر التطبيق |

## 7. إدارة الحالة

**GetX** بالكامل — لا `setState` ولا `StatefulWidget` في أي مكان. كل Controller يستخدم متغيرات تفاعلية `.obs`، والشاشة تستمع عبر `Obx(() => ...)`. التنقل يمر عبر `app_routes.dart` (أسماء الطرق كثوابت من `app_strings.dart` أو ملف منفصل) و`app_pages.dart` (يربط كل route بـ View + Binding الخاص فيه).
